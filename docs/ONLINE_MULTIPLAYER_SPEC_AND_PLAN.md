# 卫戍协议同盟联机：规则调研、技术规格与开发计划

> 调研日期：2026-10-05（Asia/Hong_Kong）；联机流程实现更新：2026-10-06。
> 目标版本：国服《卫戍协议：盟约》下半期，锚点 2026-03-14 及其后续修正  
> 开发分支：`online`，基线 `146e638dc47588428c20f2ad1624c23f9a56c6b4`  
> 文档状态：规则调研与实施规格；S7.2 匹配／信令服务和基础联机流程已实现，战斗仍由客户端模拟，端到端实际联调待完成。

## 1. 目标与结论

本项目要增加的是“同盟模拟”合作联机模式。每名玩家仍经营自己的阵地和商店；服务器把各自战斗结果汇总，在需要时组织联防，并在最终领袖战合并队伍目标生命值。核心工作不是让多名客户端共享一个本地存档，而是增加一个按玩家隔离、按回合协作、由服务器推进阶段的权威对局。

本轮调研得到的开发结论：

1. 单人和同盟共享卫戍协议的主要经营及战斗规则，但同盟有房间、成员准备、限时决策、逐人初始策略、联防、观战和共同领袖战。
2. 联机客户端不能各自决定回合何时推进。必须由同一权威服务判定阶段、截止时间、有效命令、联防结果和结算。
3. 首个技术 MVP 是 `server/` 下的匹配／信令服务：房间码、按难度快速匹配、成员状态和 WebRTC 信令中继。客户端接入与权威游戏流程分阶段继续开发。
4. 特殊决策超时由服务端在当前候选项中随机选择；当至少 3 名玩家完美作战时，从完美作战者中随机选 2 人联防。入门教学模式不纳入开发范围。
5. PRTS 详细规则用于理解当前游戏行为；官方公告用于确认重要更新。原作没有公开说明的断线恢复行为按本项目服务规则定义，不伪装成原作事实。

## 3. 单人模拟和同盟模拟的机制差异

| 维度 | 独立模拟（单人） | 同盟模拟（多人） | 依据及实现含义 |
| --- | --- | --- | --- |
| 玩家数 | 1 人 | 房间最多 4 人（房主 + 3 名成员）；2026-03-14 后可由房主取消“未满 4 人时搜寻队友”并以不足 4 人开局 | [PRTS] [官方]；服务端容量固定 4，开局人数策略必须是房间设置 |
| 进入方式 | 选难度后开始本地模拟 | 快速／精确匹配，或创建联合模拟房间后邀请／搜寻队友 | [PRTS]；MVP 先实现房间码，不依赖账号体系 |
| 房间权限 | 无 | 房主可改难度、邀请／搜人、踢人；成员可准备、离开；成员可以查看名片、申请好友（原作同服能力） | [PRTS]；本项目只做本地化需要的房主和成员角色，不做官方好友服务 |
| 入门教学 | 本项目不纳入 | 本项目不纳入 | 用户明确指定；后端仅允许四种正式 `mode_multi_*` 难度 |
| 局内交流 | 无队友沟通需求 | 可使用部分表情交流 | [PRTS]；表情事件可后置，不阻塞战斗闭环 |
| 开局准备 | 自己开始 | 成员加入后准备；是否未满 4 人开始是房间规则 | [PRTS] [官方]；准备状态由服务器检查 |
| 开局策略 | 单人选择自己的初始策略 | 所有玩家依次选择各自初始策略；联合模拟策略阶段允许一次跳过 | [PRTS]；选择顺序和跳过状态均为共享房间状态 |
| 每回合整备时间 | 决策时间无限；下半期还可以暂离后在 24 小时内恢复 | 每回合有 70 秒决策时间；整备可以查看队友当前布置，单人准备完成后可撤销，所有人均准备后进入战斗 | [PRTS]；官方公告所说 24 小时暂离只明确适用于单人，不照搬为在线房间恢复时长 |
| 整备经营 | 自己调整单位、装备、商店、资金 | 每人继续经营自己的阵地；可以查看队友布置，各自准备 | [PRTS]；服务端状态必须按 `playerId` 隔离，不能让一个玩家修改他人阵地 |
| 普通战斗 | 自动部署并自动作战 | 每名玩家分别抵御自己的敌人；全员完成作战后才进入后续阶段 | [PRTS]；所有客户端同步显示服务端阶段和结算，不由最先结束的一端推进 |
| 战中手动输入 | 可干预操作依该模式自动处理 | 与代理作战类似，部署和可干预技能操作由系统自动处理 | [PRTS]；不能把当前网页战斗输入直接视为在线指令；联机阶段以共享模拟规则驱动 |
| 失败后的补救 | 自己承担漏怪后果 | 有玩家失败而有玩家完美时，触发联防：最多 2 名完美玩家接收所有失败玩家未击倒敌人的集合 | [PRTS]；需增加联防派发、复用当前阵地状态和敌人汇总规则 |
| 目标生命 | 单人自己的目标生命 | 普通回合仍按未击倒敌人归属扣除对应玩家目标生命；进入最终领袖轮时，所有存活玩家剩余目标生命合并 | [PRTS]；每名玩家保留自己的分账，Boss 阶段另维护团队池 |
| 特殊决策 | 特定回合的 3 选 1 | 多人决策改为每名玩家 6 选 1；PRTS 标注首位 30 秒，其余玩家每人 16 秒；超时由服务端在当前候选项中随机选择 | [PRTS] 给出候选数和时限；随机超时为用户明确指定的本项目规则 |
| 难度解锁 | 单人难度进度 | 单人／同盟难度解锁互通 | [官方]；本项目的本地档案应共享相应解锁记录 |
| 模拟重载时间 | 开局后 48 秒内结束不能立即开始下一次模拟 | 同样为 48 秒 | [PRTS]；若复刻该限制，作为一次模拟结束后的冷却状态，而非房间对局计时 |
| 玩家阵亡 | 本局结束 | 阵亡成员可以继续观战 | [PRTS]；需要只读观战状态及玩家控制权撤销 |
| 主动退出 | 退出后按完成回合结算；下半期改为可暂离并于 24 小时内返回 | 玩家可离开且不影响其他人；非最后一名、未阵亡的主动退出者不获认证／奖杯，首名主动退出另有递增禁入惩罚 | [PRTS]；本项目可以复现对局内状态，但不对官方账号发奖励或施加惩罚 |
| 最终攻势 | 单人独立对抗 Boss | 目标生命合并；两名成员处于同一侧战场，部分领袖会在左右侧同时出现且共享一份总生命，所有队员共同造成伤害；Boss 战计时结束后每超时 1 秒扣 1 点目标生命 | [PRTS] [官方]；服务端需要一个统一 Boss HP 账本，不能给每客户端各自拷贝独立 HP |
| 隐秘核心 | 险境或绝境满足条件时可进入 | 同盟也按条件进入；同盟奖杯属于同盟模式专属 | [PRTS]；解锁条件、多人结算仍需按该期数据逐项接入 |
| 内容差异 | 单人难度对应 `mode_single_*` | 同难度另有 `mode_multi_*` 和多人撤离战模板 | [仓库数据]；不得只切换界面后假设全部规则与单人完全相同 |

### 3.1 需要分开的两套计时

PRTS 说明中的 **70 秒** 是普通回合整备／决策时限；**30 秒和 16 秒** 是多人特殊决策逐人选择的时限。它们是不同阶段、不同截止点。特殊回合会出现装备／悬赏／战斗加成等不同选择，候选内容依决策类型而变，不能把“6 选 1”简化成固定选项卡。服务端应分别表达为 `prepDeadline` 和 `choiceDeadline`，客户端只显示服务器给出的剩余时间。

固定仓库数据 `data/modes/alliance-lower/source.json` 的配对模式中，单人 `specialPhaseTime` 为 150，多人对应值为 16。它可以印证多人选择时限字段，但 150 与 PRTS 对单人“无限回合决策时间”的描述并不能直接对应；在确认该字段具体生效范围前，不将它解释为单人整备时限。

### 3.2 联防和最终攻势的精确规则

- 只有完美作战玩家能作为联防阵地；最多选 2 名。失败玩家未击倒的敌人集合进入联防，不能继续叠加第二层联防。
- 联防阵地保留上一阶段状态：干员／召唤物按整备期位置部署，生命比例和技力按上一阶段结束时恢复；上一阶段已退场的干员仍保持退场。具体边界以 PRTS 帮助页为准。
- 若 1–2 名玩家完美，完美者进入联防；若至少 3 名玩家完美，由服务端从完美者中随机抽取 2 人。随机结果记录并广播，作为本项目明确规则。
- 普通回合按漏怪数量扣除其所属玩家的目标生命，每回合最多扣 10 点；Boss 计时结束后战斗继续，每多 1 秒扣除 1 点团队目标生命。两种扣除分别记入事件和生命账本。
- 最终攻势把玩家剩余目标生命相加。官方公告确认部分领袖会在左右侧同时出现；两侧共享该领袖的一份总生命，不因展示两个 Boss 而增加总血量。
- 最终领袖轮中不能通过战斗内效果继续叠加层数；特定策略、盟约或装备在 Boss 阶段的效果需按该期数据核对。
- PRTS 记录提示领袖不受侵蚀损伤，最终攻势战场按两人一组；两组不能互看阵地。具体分组、空缺玩家时的战场布局和同一房间少于 4 人时如何成组，需要实测。

## 4. 完整联机对局流程

```text
大厅
  → 创建房间 / 输入房间码加入
  → 校验难度、内容版本、人数与房主设置
  → 全员准备 / 房主开局
  → 逐名玩家选择初始策略（允许按规则跳过一次）
  → 展示模拟简报和随机地图
  → 每回合整备（70 秒 / 全员准备即提前结束）
  → 各玩家独立自动战斗
  → 等待所有仍参战玩家完成
      ├─ 全员完美：回合结束
      ├─ 有失败且有完美：最多两人联防后回合结算
      └─ 按敌人归属扣除目标生命、阵亡者转观战
  → 特殊回合的逐人选择（6 选 1，首位 30 秒、其余 16 秒；超时随机选择）
  → 最终领袖战（团队目标生命池、共享 Boss 生命）
  → 达成条件时进入隐秘核心
  → 服务端统一结算并保存战绩
```

这里的流程顺序以 PRTS 当前说明为准；特殊决策具体插入哪一轮、是否与整备界面合屏，应由固定版本页面录屏核实。阶段机要允许按配置在普通回合间插入机变／悬赏等特殊节点，不能把整个流程写成只支持固定长度的硬编码状态。

## 5. 仓库当前情况和联机缺口

### 5.1 已有基础

- 项目主入口是 `dist/native-*` 客户端；S7 已在 [DEVELOPMENT_PLAN.md](../DEVELOPMENT_PLAN.md) 定义“同盟模拟与协作界面”的阶段目标和验收标准。
- `dist/native-lobby.js` 当前显式过滤 `modeType === 'MULTI'`，所以用户界面不会列出同盟模式。
- `NativeSession` 能接收 `playerId`、`teamPeers`、`teamTransport`；下半期里有“巫恋类队友转移”收件箱／发件箱、收件去重和发送钩子。这些是局部协作机制接口，不是房间、服务端权威状态或网络恢复实现。
- 下半期源数据在 `data/modes/alliance-lower/source.json`。目前每个正常难度有单人和多人模式 ID；单人和多人战场模板在 `constData.escapedBattleTemplateMapSinglePlayer`、`constData.escapedBattleTemplateMapMultiPlayer` 分别指向 `_single` 和 `_multi`。
- 同一难度的单人／多人配置大体复用盟约和禁用敌人名单；`modeType`、`specialPhaseTime` 及描述不同。标准难度的活动盟约数量是 13，其余当前正常难度是 23。模式字段相近不能证明底层撤离战、Boss 阶段和奖励全部相同。
- 项目当前单人最终 Boss 血量沿用了四人配置的 0.75 倍默认值（见 `AGENTS.md`）。在线接入不能不加区分地复用该单人系数；应按多人活动模板的实际总生命配置，在本地多人跑通后核对。

### 5.2 当前 MVP 和剩余能力

大厅已支持房间码创建／加入、正式多人难度、最多 4 人、默认允许 2–3 人开局、成员准备和房主开局。房间开始后客户端通过房间信令建立全网状 WebRTC DataChannel，再各自进入独立的多人 `NativeSession`。服务端为本局生成公共种子和阵地 ID；各客户端据此统一地图、波次和最终 Boss，并按玩家 ID 分开本地随机流。已有盟约干员转让接口现可经 `team.fang` 消息发给对应队友，`peer.status` 同步盟约人数供转让选择使用。

这属于连接与协作验证 MVP，不是完整同盟对局：服务端目前不承载游戏命令、权威事件流、阶段计时、联防协调、共享 Boss 状态、只读观战或多人结算；玩家的战斗和轮次仍可各自推进。超时随机决定和“3 名以上完美者时随机选 2 人联防”已写入规则钩子与用户决策，但尚未接入实时对局阶段。快速匹配 API 已在服务端实现，当前大厅只提供配对码入口。

### 5.3 版本数据观察

调研脚本对 `FUNNY`、`NORMAL`、`HARD`、`ABYSS` 的单人／多人 `modeDataDict` 做了字段比较。除 `modeType`、ID／展示描述、`specialPhaseTime` 等元数据外，配对模式的主要盟约和禁用敌人字段相同；撤离战模板明确分开。此比较只描述仓库中的模式元数据，不代表战斗事件、敌人数、Boss 血量或奖励完全相同。

官方公告确认 2026-03-14 后同盟房间在“未满 4 人时搜寻队友”未勾选时可以不足 4 人开局，也确认单人和同盟协议的解锁状态互通。PRTS 中的多人入门协议只能用预设干员且不发卫戍认证／解锁策略；用户已明确项目不实现该教学模式。服务端将只允许 `mode_multi_funny`、`mode_multi_normal`、`mode_multi_hard`、`mode_multi_abyss` 四种正式难度。

## 6. 建议技术规格

本节均为 **[设计提案]**，目的是让多人操作可验证、可恢复；它们不是 PRTS 对原作网络协议的描述。

### 6.1 权威边界

1. **服务端是唯一对局权威。** 客户端提交意图命令；服务端鉴权、校验阶段和玩家归属，执行模拟并广播已接受的状态／事件。客户端可以做操作预览，但不能本地先改正式资源再等待服务端确认。
2. **房主只拥有房间管理权。** 房主可以改难度、邀请或移除未开局成员、决定开始；进入模拟后房主断线不应令对局主状态消失，也不获得他人阵地写权限。
3. **复用同一模拟核心。** 每名玩家拥有自己的 `NativeSession`／状态分区，共享一个房间协调器、相同内容版本和明确的联机事件序号。游戏权威状态最终由服务端协调；信令阶段的 WebRTC DataChannel 只用于客户端传输技术验证，不能自行决定正式游戏状态。
4. **房间固定最多 4 个玩家槽。** 房间有 `roomId`、`runId`、创建者、难度、模式版本、内容哈希、房间码、槽位、准备状态和开局设置。已开局离开的槽位成为空／离开／阵亡状态，不能悄悄由新玩家接管局内角色。
5. **阶段时钟使用服务器时钟。** 阶段开始时存绝对截止时间；客户端按该时间绘制倒计时，切后台不会暂停；短暂网络延迟只影响消息到达，不应让客户端各自算出不同的推进时点。

### 6.2 命令与事件信封

建议统一 JSON 信封，样例：

```json
{
  "protocolVersion": 1,
  "roomId": "room-id",
  "runId": "run-id",
  "commandId": "client-generated-unique-id",
  "expectedRevision": 42,
  "type": "prep.command",
  "payload": { "op": "move-unit", "unitId": "u-7", "to": 3 }
}
```

- 身份由连接票据确定；服务端不能信任客户端 payload 里的 `playerId`。
- `commandId` 去重；同一命令重传只返回原结果，不重复花钱或移动单位。
- `expectedRevision` 防止基于旧状态的双击／并发提交；冲突时回传拒绝原因和最新修订号。
- 每个命令必须校验玩家控制权、当前阶段、资金／槽位／规则约束及内容版本。
- 服务端用单调递增 `revision` 广播 `command.accepted`、`command.rejected` 和对局事件。阶段跳转是服务器生成的事件，不允许客户端调用“下一回合”。
- 重要事件带 `eventId`、`runId`、`revision`、`phaseId`、逻辑时间、种子／随机流位置和必要来源，以便幂等重放和查错。

推荐命令集合先保持小而明确：`room.setSettings`、`room.kick`、`room.ready`、`room.start`、`strategy.choose`、`strategy.skip`、`prep.command`、`prep.ready`、`specialChoice.choose`、`player.leave`、`room.rejoin`、`emote.send`。数据面不要把任意 JavaScript 或整段客户端 Session 状态当成指令。

### 6.3 服务器阶段机

建议房间级阶段：

`WAITING_ROOM → STRATEGY_SELECTION → BRIEFING → PREP → BATTLE → JOINT_DEFENSE? → ROUND_SETTLEMENT → SPECIAL_CHOICE? → PREP … → FINAL_ASSAULT → SECRET_CORE? → SETTLEMENT`。

玩家级状态与房间级阶段分开保存：`READY / ACTIVE / BATTLE_DONE / DEFEATED / DISCONNECTED / LEFT / SPECTATING`。房间级阶段只有服务器推进。普通战斗阶段允许不同玩家在各自仿真中结束，但服务器在应参战成员都完成、阵亡或按超时规则处理后，才统一进入结算。联防是房间阶段，失败玩家只观战；参与者使用该回合结束时状态和统一敌人集合。

### 6.4 断线、重连和超时建议

PRTS 已查页面说明阵亡可观战和玩家可退出，但未找到同盟掉线恢复细则。因此必须把下述条款标作本项目服务规则，在联机文档和房间 UI 说明：

- 心跳丢失先将成员标成 `DISCONNECTED`，而不是马上 `LEFT`；恢复连接后用短期签名票据验证原成员身份。
- 在线局不因一人断线暂停所有人的时钟或战斗。整备阶段保留该玩家最后一次有效状态；阶段到期后按预先定义的默认行为提交／准备。该默认行为不能消费未确认的客户端操作。
- 特殊选择超时由服务端使用安全随机数从该玩家当前仍有效的候选项中等概率选一项，并广播／记录实际结果；重连和事件重放复用已记录结果，不重复抽取。首位 30 秒和后续 16 秒以服务器阶段时钟为准。
- 联防候选达到 3 人时，服务端无放回随机抽取 2 人并记录／广播结果；候选不足 3 人则全部参加。不能由每个客户端各自掷随机数。
- 恢复流程先发当前房间与玩家快照，再按 `revision` 补发尚未确认事件；如事件历史已清理则只给快照。重复重连不重复执行命令。
- 退出是显式 `LEFT`；断线是可恢复的 `DISCONNECTED`；阵亡是 `DEFEATED` 并切为只读观战。三者不能共用一个布尔值。
- 服务器定期保存房间快照和有限事件日志。对局保留时长、异常退出后的清理周期尚无原作依据，作为本项目可配置运维策略决定；不得直接套用单人 24 小时暂离规则。

### 6.5 服务接口和部署边界

- 当前 S7.2 的首个 MVP 是 Node.js 自建 HTTP + WebSocket 匹配／信令服务：HTTP 提供健康检查；WebSocket 处理房间创建／房间码加入／快速匹配／成员状态和 WebRTC offer、answer、ICE 候选转发。WebRTC DataChannel 用于连接验证；正式游戏状态权威服务端、房间规则、计时、联防和结算属于后续阶段。
- 这套信令服务为以后服务端权威对局保留稳定协议、房间成员身份和服务端随机决策入口。HTTP 健康检查、信令和模拟服务必须有清晰边界，不能把仓库静态网页服务器当成游戏权威服务。
- 开发期一个进程持有房间和内存状态，另加本地持久化快照／事件日志。进程重启恢复属于 S7 稳定性目标；多进程房间分片、集群和公开服务鉴权后置。
- 房间码必须随机、短期有效、速率限制；加入房间需要成员票据。不要把可猜测顺序 ID 当成加入密钥。
- 运行版本握手至少包含 `protocolVersion`、`gameBuildId`、`contentPackId`、`contentHash` 和难度／模式 ID。规则或固定数据不一致时拒绝加入，不静默混跑。
- 只从可信静态文件加载游戏规则，联机命令只接受 schema 白名单操作。服务端对槽位上限、包大小、频率和非法身份做硬限制。
- 部署第一目标是开发机／同一局域网可运行的自建服务；公网 HTTPS、反向代理、备份、更新回滚和匿名滥用限速列入发布阶段。

### 7.1 MVP 范围

当前 MVP 包含 `server/` 配对和信令服务、配对码大厅、WebRTC 连接，以及服务器负责的普通回合栅栏。流程为创建 → 分享 6 位配对码 → 加入 → 全员准备 → 房主开始 → 建立点对点连接 → 进入各自的多人难度模拟。每名玩家运行独立阵地；公共地图、波次和 Boss 回合一致，商店随机流按玩家分开；盟约干员转让通过 DataChannel 发送。

普通战斗结束后，各客户端提交漏怪数、漏过敌人 ID／路线和阵亡状态。服务端等全部活动玩家提交后，若既有漏怪者也有完美作战者，则安排联防：完美者不超过 2 人时全员参加，达到 3 人时服务端无放回随机选 2 人；漏怪敌人分配给入选者。联防回报后，存活成员通过全员确认栅栏推进下一回合。到 Boss 回合时，全员报告并直接结束本局，不运行 Boss 战。

本 MVP 的战斗仍由每个客户端独立模拟，服务端不验证战果、敌人状态或资源，也不提供整备／决策计时、超时随机选择、Boss 共血量、完整掉线恢复、账号好友、奖杯精确匹配、TURN 中继和官方奖励。当前服务随机规则中“特殊决策超时随机选有效候选”尚未接入玩法；不实现入门教学模式。

### 7.2 后续验证矩阵

已执行验证：`node --test tests/online-coop.test.mjs` 的 4 个联机用例通过；本地 Edge 的 4 个独立浏览器上下文通过配对码创建／加入、全员准备、点对点连接和进入对局，页面错误为 0。自动化用例覆盖服务端四客户端回合栅栏、联防和 Boss 跳过，以及 NativeSession 实际创建联防战斗和跳过 Boss。还未用浏览器实际跑完整普通战斗至漏怪、进入联防再结算。

下表其余场景仍是后续验收项目：

| 场景 | 需要证明 |
| --- | --- |
| 1、2、3、4 人开局 | 成员数和未满员选项生效；不会出现空玩家提交或悬挂等待 |
| 两人同时编辑／重复提交 | 冲突按 revision 拒绝或按序处理；重复命令只改变一次状态 |
| 房主中途断线 | 已开始对局继续；房主回来可恢复同一身份和当前状态 |
| 普通成员断线／重连 | 其他成员的计时和战斗继续；该成员快照、序号和命令结果连续 |
| 超时和最后一刻提交 | 服务器截止顺序稳定；截止之后命令被拒绝；阶段只推进一次 |
| 联防组合 | 0、1、2、3 个完美玩家以及多个失败者；随机抽取结果单次广播一致、记录可重放 |
| Boss 两侧同步 | 两侧 Boss 共享一个总 HP；所有玩家伤害只扣一次；超时扣团队目标生命 |
| 版本／内容哈希不一致 | 加入／开始时拒绝并显示可操作原因 |
| 阵亡、离开、观战 | 控制权限立即撤销，观战端只读，其他玩家可继续 |
| 服务进程重启 | 房间和票据当前为内存状态，确认重启后失效；未来增加持久化时，已经确认的命令不重放执行 |
| 现有单机模式 | 无房间服务时仍能正常开局、存档和结算；多人加入不改变单机计时／状态 |

## 8. 2026-10-06 联机流程实现口径

本节记录用户确认的 MVP 实际行为，优先级高于旧计划中的实现建议；原作数据与项目实现差异分开标注。

| 流程 | 当前实现 | 规则依据／差异 |
| --- | --- | --- |
| 房间开局 | 全员准备后由房主确认；`room.started` 后客户端自动进入简报和策略选择，不要求手动点击进入 | PRTS 帮助页描述同盟玩家按顺序选择策略。 |
| 初始策略 | 服务端随机排列房间内玩家；策略不能重复。首位 30 秒，后续每位 15 秒；超时从该玩家未被选的可用策略中随机抽取。全员选择后倒计时 5 秒并自动开始 | PRTS 帮助页记载首位 30 秒、后续 16 秒；项目依用户确认将后续改为 15 秒，并明确超时随机。 |
| 整备 | 所有存活成员同时进入整备，最多 90 秒；玩家主动点“我已准备”，全员准备或时限到即自动战斗 | PRTS 帮助页记载休整期 70 秒；项目按用户明确需求取 90 秒。 |
| 战斗与联防 | 客户端各自模拟战斗；服务端等待全部活动成员提交。存在失败和完美者时，以完美阵地联防；3 名以上完美者随机无放回选 2 名。未被击倒的联防敌人携带原失败玩家归属。 | 联防与候选数量依据 PRTS 帮助页；3 人以上的随机抽选依据本项目先前确认的联机规则。 |
| 回合生命与继续 | 服务端按联防后剩余敌人归属扣除个人目标生命，每人每回合最多 10 点；同步回合结算后自动进入下一轮整备 | PRTS 帮助页记载按归属扣目标生命、每回合最多 10 点；自动继续整备为当前项目流程。 |
| 服务实现 | `CoopGameCoordinator` 保存选择／准备／战斗阶段状态；Cloudflare Durable Object Alarm 推进 30／15／5／90 秒截止，本地 Node 服务使用定时器。简报区纵向显示四个槽位、玩家 ID、状态和已选策略；整备区显示各玩家准备状态。 | 项目实现事实；服务器校验阶段和回报格式，但不验证客户端战斗模拟真伪。 |

本流程不实现入门教学。最终 Boss 共用生命、战场拼接与特殊机变／悬赏选择仍未接入；目前到 Boss 阶段沿用 MVP 跳过结局。端到端多浏览器联调和 1–4 人实际场景仍需继续验收。
